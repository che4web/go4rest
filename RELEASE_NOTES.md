# go4rest v0.2.0

Основное изменение — права на модели и отдельные объекты,
несколько ролей у пользователя и защищённое управление назначениями.
Требуемая версия Go: **1.24.2 или новее**.

## Новые возможности

- Четыре стандартных права для модели: `view`, `add`, `change`, `delete`.
- Несколько ролей у пользователя; права всех ролей и прямые назначения
  складываются.
- Объектные разрешения для пользователей и ролей. Модельное разрешение даёт
  доступ ко всем объектам, объектное — к конкретной записи.
- Фильтрация `List` и `Full` до подсчёта `count` и пагинации.
- Поддержка `IsSuperuser`.
- Настройка авторизации через опцию конструктора `auth.ModelPermissions`.
- API просмотра разрешений, назначения и отзыва ролей, модельных и объектных
  прав.
- CLI-команды `startproject` и `startapp`. Новые проекты используют
  `github.com/che4web/go4rest v0.2.0`; существующие каталоги не перезаписываются.

### Подключение прав в конструкторе

```go
func NewProductController(db *gorm.DB) *ProductController {
    return &ProductController{
        ViewSet: go4rest.NewViewSet[Product](
            db,
            auth.ModelPermissions("catalog.product"),
        ),
    }
}
```

Создание контроллера и регистрация CRUD-маршрутов сохраняют прежний вид:

```go
products := NewProductController(db)
go4rest.RegisterCRUDRoutes(router, "products", products)
```

Опция регистрирует права и подключает проверки автоматически. Таблицы
авторизации должны быть мигрированы до создания защищённого контроллера;
ошибка инициализации останавливает конструктор через `panic`.
Вызов `go4rest.NewViewSet[Product](db)` без опций остаётся публичным.

## Изменения совместимости

### Пользователи и роли

- CRUD `/api/user/` и `/api/user_role/` теперь защищены разрешениями
  `auth.user` и `auth.role`.
- Публичный `/api/register` больше не назначает роль из `role_id`.
- Создание и обновление пользователя принимают только `username` и `password`;
  вложенные роли, права и `IsSuperuser` через эти операции не назначаются.
- Для смены пароля через `PUT /api/user/:id/` нужны право `change` на целевую
  запись и дополнительное **модельное** `auth.user` / `change_password`.
  Новое право не выдаётся существующим пользователям автоматически.
- Обновлять имя или пароль superuser может только superuser, даже если другой
  пользователь имеет `change_password`.
- `/api/who_i` возвращает `roles`, `permissions` и `is_superuser` вместо
  прежнего единственного поля `role`. Клиенты должны обновить обработку ответа.
- `User.RoleID` и `User.Role` сохранены как устаревшие поля совместимости;
  авторизация использует `User.Roles`. Отзыв роли очищает совпадающий `RoleID`.

### Сессии

Встроенный ключ `secret` удалён. Постоянный ключ длиной минимум 32 байта
передаётся явно:

```go
auth.RegisterRoutes(router, db, signingKey)
```

Без ключа генерируется случайный ключ на время жизни процесса. Для нескольких
экземпляров приложения нужен общий постоянный ключ. Сессии прежней версии
с ключом `secret` недействительны: пользователям потребуется войти заново.
Cookie использует `HttpOnly` и `SameSite=Lax`.

### CRUD и фильтры

- В защищённых стандартных `Create` и `Update` отключено сохранение вложенных
  ассоциаций. Для операций над связями с отдельной политикой доступа используйте
  собственные DTO/обработчики.
- `PreloadField` относится к данным доступного корневого объекта; права на
  связанные модели автоматически не проверяются.
- Обновление сохраняет исходный первичный ключ и больше не выполняет upsert.
  Исчезнувшая запись возвращает `404`; обновление существующей записи без
  изменения значений остаётся успешным.
- Поля фильтрации и сортировки проверяются по GORM-схеме и экранируются.
  SQL-выражения и поля с `json:"-"` не допускаются в качестве полей запроса.
- Без действующей сессии защищённые операции возвращают `401`. Отказ в
  операциях, требующих общего модельного права (создание, схема, назначения,
  смена пароля), возвращает `403`; недоступный конкретный объект — `404`.
  Списки содержат только доступные объекты и могут быть пустыми (`200`).

## Обновление базы данных

### Старая одноролевая схема

Если `user_roles` ещё нет, обычный `auth.Migrate(db)` или `auth.RegisterRoutes`
однократно переносит назначения `RoleID` в новую связь. Названия старых ролей
не превращаются автоматически в разрешения: настройте их права отдельно.

### Промежуточная многоролевая схема

Если `user_roles` уже существует, автоматическая миграция сохраняет текущие
назначения. Она не восстанавливает роли из устаревшего `RoleID`, в том числе
при обновлении с промежуточной версии без отметки миграции.

### Заранее созданная таблица связи без переноса назначений

Если `AutoMigrate(&auth.User{})` только создал схему, а актуальные назначения
по-прежнему находятся в `RoleID`, выполните явный импорт **до первого обычного
вызова миграции или регистрации auth-маршрутов**:

```go
if err := auth.Migrate(db, auth.RoleMigrationImportLegacy); err != nil {
    log.Fatal(err)
}
auth.RegisterRoutes(router, db, signingKey)
```

Доступные режимы:

| Режим | Поведение при первой миграции |
|---|---|
| `RoleMigrationAuto` — по умолчанию | Импорт из старой схемы без `user_roles`; сохранение существующей многоролевой схемы |
| `RoleMigrationPreserve` | Сохранение текущих назначений без импорта `RoleID` |
| `RoleMigrationImportLegacy` | Явный однократный импорт актуальных `RoleID` |

Выбор источника и перенос фиксируются атомарно в `auth_schema_migrations`.
Неудачный импорт можно повторить. Завершённый импорт не повторяется, а режим
сохранения нельзя позднее переопределить импортом; новые назначения выполняйте
через сервис или API.

Первого superuser создайте или настройте явной доверенной операцией
инициализации. Пример создания приведён в [AUTHORIZATION.md](AUTHORIZATION.md).
`auth.RegisterRoutes` должен вызываться до регистрации прикладных маршрутов,
чтобы middleware сессий применялся к ним.

## API назначений

| Метод и маршрут | Назначение |
|---|---|
| `GET /api/permissions` | Каталог доступных разрешений |
| `POST /api/role_assignments` | Назначить роль |
| `DELETE /api/role_assignments` | Отозвать роль |
| `POST /api/permission_assignments` | Назначить модельное или объектное право |
| `DELETE /api/permission_assignments` | Отозвать право |
| `GET /api/object_permissions` | Просмотреть объектные назначения |

Управление назначениями требует модельного `auth.permission` / `change`.
Просмотр всех объектных назначений требует `auth.permission` / `view`.
Успешная выдача/отзыв возвращает `204`; повторные операции идемпотентны.
Форматы JSON и программный интерфейс описаны в [AUTHORIZATION.md](AUTHORIZATION.md).

## Исправления безопасности и целостности

- Обычное право редактирования пользователя больше не позволяет захватить
  привилегированную учётную запись через смену пароля.
- Изменение `id` в теле запроса не перенаправляет обновление на другую запись.
- `Update` не восстанавливает удалённую запись без права `add` и сохраняет
  объектное ограничение доступа в SQL-запросе записи.
- При окончательном удалении через защищённый ViewSet объектные назначения
  очищаются в той же транзакции. При ошибке очистки удаление откатывается.
- Удаление пользователя или роли также очищает назначения получателя и связи
  с ролями/модельными правами, включая SQLite без внешних ключей.
- Soft-delete сохраняет назначения, но мягко удалённые роли не участвуют
  в проверках прав.
- Для собственных обработчиков окончательного удаления доступен
  `PermissionService.DeleteObjectPermissions(tx, model, objectID)`; вызов должен
  выполняться в той же транзакции, что и удаление.
- Пароли и их хеши больше не выводятся диагностическими сообщениями в stdout.

## Проверки перед публикацией

```sh
go test ./...
go vet ./...
git diff --check
```

Интеграционные проверки выполняются на SQLite. Тест
`TestGeneratedProjectUsesReleaseArtifact` собирает локальный архив модуля
`v0.2.0` и проверяет сгенерированный проект через Go module proxy без `replace`,
в отдельном module cache. Он также проверяет доступность нового API и реальную
проверку авторизации. Это проверка подготовленного артефакта, а не подтверждение
публикации версии в публичном proxy.
