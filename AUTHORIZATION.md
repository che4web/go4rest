# Роли и разрешения

## Подключение

`auth.RegisterRoutes` мигрирует таблицы авторизации, регистрирует стандартные
права для `auth.user`, `auth.role`, `auth.permission` и подключает cookie-сессии.
Вызывайте его **до регистрации прикладных маршрутов**, чтобы middleware сессий
применялся к ним.

```go
// signingKey — постоянный секрет приложения длиной не менее 32 байт.
auth.RegisterRoutes(router, db, signingKey)

products := NewProductController(db)
go4rest.RegisterCRUDRoutes(router, "products", products)
```

Авторизация настраивается внутри конструктора контроллера:

```go
type ProductController struct {
    *go4rest.ViewSet[Product]
}

func NewProductController(db *gorm.DB) *ProductController {
    return &ProductController{
        ViewSet: go4rest.NewViewSet[Product](
            db,
            auth.ModelPermissions("catalog.product"),
        ),
    }
}
```

`auth.ModelPermissions` автоматически регистрирует четыре стандартных права
модели и подключает модельную и объектную авторизацию. Повторное создание
контроллера не дублирует права. Таблицы авторизации должны быть мигрированы
через `auth.RegisterRoutes` или `auth.Migrate` до создания контроллера.
Некорректное имя модели или ошибка регистрации прав останавливают создание
ViewSet через `panic`, чтобы приложение не запустилось с неработающей защитой.

Прежний вызов `go4rest.NewViewSet[Product](db)` сохраняет публичное поведение.
Интерфейс контроллеров и `RegisterCRUDRoutes` не меняются.

Без переданного ключа
`RegisterRoutes` генерирует случайный ключ: после перезапуска сессии станут
недействительными. Несколько экземпляров приложения должны использовать один
постоянный ключ. Старые сессии, подписанные встроенным ключом `secret`, также
станут недействительными.

Если нужны только модели/сервис без HTTP-маршрутов, вызовите `auth.Migrate(db)`
и подключите middleware `gin-contrib/sessions` самостоятельно.

## Семантика

У каждой зарегистрированной модели есть четыре права: `view`, `add`, `change`,
`delete`. В БД право хранится парой `model` / `action`, например
`catalog.product` / `view` (аналог Django `catalog.view_product`).

У `auth.user` дополнительно регистрируется право `change_password`.

- Все роли пользователя и прямые назначения складываются.
- Модельное право разрешает действие над всеми объектами модели.
- Объектное право разрешает действие над одной записью. Оно может принадлежать
  пользователю или роли. Запретов и приоритетов ролей нет.
- `List` и `Full` без общего `view` показывают только разрешённые объекты.
  Ограничение применяется до пользовательских фильтров, подсчёта и пагинации.
  При отсутствии доступных объектов возвращается пустой список.
- `Create` требует модельного `add`; объектные назначения `add` запрещены.
- `Update` сохраняет ограничение доступа в SQL-запросе и никогда не вставляет
  запись заново. Если объект удалён или объектное разрешение отозвано между
  чтением и обновлением, возвращается `404`. Обновление без изменения значений
  существующей доступной записи остаётся успешным (`200`).
- При окончательном удалении через защищённый ViewSet все объектные назначения
  для этой модели и ключа удаляются в той же транзакции. Назначения на другие
  объекты или модели не затрагиваются. Ошибка очистки откатывает удаление.
- При окончательном удалении пользователя или роли также очищаются их
  объектные назначения на остальные модели, связи с ролями и модельными правами
  (включая SQLite с выключенными внешними ключами). Soft-delete сохраняет назначения;
  мягко удалённые роли при проверке прав не учитываются.
- `Schema` требует модельного `view`.
- `IsSuperuser` даёт все права.

Без действующей сессии защищённые обработчики возвращают `401`. Недостаточно
модельных прав на создание, схему или управление назначениями — `403`.
Недоступный объект в detail/update/delete возвращает `404`.

Стандартный ViewSet использует числовые ID в URL. `object_id` в назначениях
передаётся строкой с каноническим значением ключа, например `"42"`, а не `"042"`.
Объектная фильтрация требует одиночного первичного ключа.

Авторизация относится к корневой модели ViewSet. Настроенные `PreloadField`
сериализуются вместе с доступной записью: права связанных моделей автоматически
не проверяются. Для связей с отдельной политикой доступа используйте собственный
обработчик/DTO. В защищённых стандартных Create/Update сохранение вложенных
ассоциаций отключено; скалярные внешние ключи остаются частью данных модели.

## Начальный администратор

Создайте superuser явной операцией инициализации, после миграции:

```go
admin := auth.User{
    Username: "admin",
    Password: initialPassword,
    IsSuperuser: true,
}
if err := admin.HashPassword(); err != nil { return err }
if err := db.Create(&admin).Error; err != nil { return err }
```

Это однократная операция, а не код для каждого запуска. HTTP API не позволяет
назначать `IsSuperuser`. Публичная регистрация принимает только username/password,
не назначает роли и не принимает права.

## API управления

Существующие CRUD `/api/user/` и `/api/user_role/` теперь защищены правами
`auth.user` и `auth.role`. Создание/обновление пользователя принимает только
`username` и `password`; пароль хешируется. Создание/обновление роли принимает
только `name`. Роли и права назначаются отдельными операциями.

Для обновления пароля через `PUT /api/user/:id/` дополнительно требуется
**модельное** право `auth.user` / `change_password`. Одного `change` на модель
или объект недостаточно. Объектное назначение `change_password` не разрешает
эту операцию. Новое право автоматически регистрируется при создании контроллера,
но существующим пользователям и ролям автоматически не выдаётся.

Право `change_password` позволяет войти под целевой учётной записью, поэтому
предназначено для доверенных администраторов учётных данных. Это относится
также к смене своего пароля через данный административный API; отдельного
сценария смены пароля с проверкой старого пароля здесь нет.

Изменять учётную запись superuser (включая username и password) может только
superuser. Даже сочетание `change` и `change_password` обычному пользователю
такой доступ не даёт. Создание нового пользователя с начальным паролем
по-прежнему требует `add`; пользователь создаётся без привилегий.

| Маршрут | Назначение | Требуемое модельное право |
|---|---|---|
| `GET /api/permissions` | Каталог разрешений | `auth.permission` / `view` (или объектный доступ к записям каталога) |
| `POST /api/role_assignments` | Назначить роль | `auth.permission` / `change` |
| `DELETE /api/role_assignments` | Отозвать роль | `auth.permission` / `change` |
| `POST /api/permission_assignments` | Назначить разрешение | `auth.permission` / `change` |
| `DELETE /api/permission_assignments` | Отозвать разрешение | `auth.permission` / `change` |
| `GET /api/object_permissions` | Просмотреть объектные назначения | `auth.permission` / `view` |
| `GET /api/who_i` | Собственные роли, их права, прямые права и признак superuser | Аутентификация |

Назначение роли (одинаковое JSON-тело для POST/DELETE):

```json
{"user_id": 7, "role_id": 2}
```

Назначение разрешения всей модели пользователю:

```json
{"user_id": 7, "permission_id": 12}
```

Назначение разрешения на объект роли:

```json
{"role_id": 2, "permission_id": 12, "object_id": "42"}
```

Обязательно указывается ровно один получатель: `user_id` или `role_id`.
Получатель и разрешение должны существовать. Наличие самого объекта не
проверяется: сервис не имеет реестра прикладных моделей. Повторная выдача/отзыв
идемпотентны. Успешные операции возвращают `204`.

Право `auth.permission` / `change` позволяет управлять всеми назначениями;
выдавайте его администраторам прав. Одного `auth.user` / `change` недостаточно
для назначения ролей или прав.

## Программный интерфейс

```go
permissions := auth.NewPermissionService(db)
err := permissions.SetRole(userID, roleID, true) // false — отозвать
err = permissions.SetPermission(userID, 0, permissionID, "", true) // вся модель
err = permissions.SetPermission(0, roleID, permissionID, "42", true) // объект роли

allowed, err := permissions.HasPermission(&user, "catalog.product", "change")
allowed, err = permissions.HasObjectPermission(&user, "catalog.product", "view", "42")
```

Методы назначения сервиса предназначены для доверенного серверного кода;
HTTP-обработчики выполняют проверку полномочий перед их вызовом. Методы
`HasPermission` принимают актуальную запись пользователя, загруженную из БД.

Если объект удаляется собственным обработчиком или напрямую через GORM,
в той же транзакции вызовите
`permissions.DeleteObjectPermissions(tx, "catalog.product", objectID)` после
успешного окончательного удаления. Автоматическая очистка стандартного ViewSet
использует необязательный интерфейс `go4rest.ObjectPermissionCleaner`;
собственные реализации авторизации могут реализовать его для своего хранилища.

## Переход со старой схемы

`auth.Migrate(db)` и `auth.RegisterRoutes` используют безопасный автоматический
режим выбора источника ролей:

- Если `user_roles` ещё нет, существующие `User.RoleID` однократно переносятся
  в новую связь. Это обычное обновление со старой одноролевой схемы.
- Если `user_roles` уже существует, её назначения сохраняются без дополнений
  из `RoleID`. Это также относится к промежуточным версиям без отметки миграции:
  старый `RoleID` мог остаться после отзыва роли и не считается разрешением.

Если таблицу связи заранее создал обычный `AutoMigrate(&auth.User{})`, а перенос
из одноролевой схемы ещё не выполнялся, явно выберите источник **до первого
вызова `auth.RegisterRoutes` или обычного `auth.Migrate`**:

```go
if err := auth.Migrate(db, auth.RoleMigrationImportLegacy); err != nil {
    log.Fatal(err)
}
auth.RegisterRoutes(router, db, signingKey)
```

Этот режим используется только когда `RoleID` действительно является актуальным
источником назначений. Для явного сохранения текущих назначений доступен
`auth.Migrate(db, auth.RoleMigrationPreserve)`; поведение по умолчанию задаёт
`auth.RoleMigrationAuto`.

Решение об источнике (`RoleMode`), возможный перенос и отметка
`user_roles_from_role_id` в `auth_schema_migrations` фиксируются в одной
транзакции. После ошибки миграцию можно повторить; после успешного завершения
источник не переопределяется и перенос не повторяется. Если уже зафиксирован
режим сохранения, попытка позднего `RoleMigrationImportLegacy` возвращает ошибку;
новые назначения в этом случае выполняются явно через `SetRole` или API.

Устаревшие поля `RoleID` и `Role` сохраняются для совместимости, но в проверках
прав не участвуют. Повторный запуск миграции не возвращает отозванные роли.
Для всех новых назначений используйте `Roles`, сервис или API назначений.
При отзыве роли сервис также очищает совпадающий устаревший `RoleID`.

Существующие прикладные API остаются публичными, пока у соответствующего ViewSet
не подключена опция `auth.ModelPermissions(...)`. API пользователей и ролей
защищается сразу. Ранее написанный код с явными `Authorizer` и `PermissionModel`
также продолжает работать.
